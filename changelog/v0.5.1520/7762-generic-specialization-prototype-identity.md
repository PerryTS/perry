### Fixed

- **Monomorphized generic specializations share the generic's prototype object (#7757, partial).** `new Gen<number>()` compiles to a second class `Gen$num` with its own class id, and each specialization materialized its **own** prototype object. So `Object.getPrototypeOf(new Gen<number>()) === Object.getPrototypeOf(new Gen<string>())` was `false` where node says `true` — and, worse, the registry contradicted itself: `getPrototypeOf(a) === Gen.prototype` was simultaneously `true`, because the answer depended on which class id you asked through.

  TypeScript erases type arguments, so at runtime there is exactly one `Gen` and one `Gen.prototype`. Both prototype registries — `CLASS_DECL_PROTOTYPE_OBJECTS` and `CLASS_PROTOTYPE_OBJECTS`, the two paths CLAUDE.md warns have disagreed about the same chain before — now resolve a specialization through `class_generic_origin`, the same edge `instanceof` uses (#7575) and the display name uses (#7632). Method dispatch is untouched: it runs off the per-class-id vtable, so each specialization keeps its monomorphized bodies.

  **`a.constructor === Gen` is still divergent and #7757 stays open for it.** That edge does not resolve through either prototype registry; redirecting `instance_constructor_value` — the obvious site, and the one `get_field_by_name_tail` calls for exactly this key — changes nothing. Two things learned while chasing it, recorded so the next attempt does not repeat them: `object_static_prototype()` appears to materialize on first call, so an added probe of it flips the very branch under test; and `class Empty {}` gives `e.constructor === undefined` (node: `Empty`), which suggests the `.constructor` gap is broader than generics rather than a monomorphization leak.

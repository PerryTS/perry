### Fixed

- **A replaced `Array.prototype[Symbol.iterator]` now drives every spread form (#7542).** `[...arr]`, `[0, ...arr, 9]`, `f(...arr)` and `Array.from(arr)` all took element-copy fast paths that never consult the iteration protocol, so a patched prototype method was ignored and the builtin element copy was returned. Node yields whatever the patched method yields.

  The issue's diagnosis needed correcting in two places, both of which changed the fix. First, `note_array_proto_iterator_write` **does** fire — instrumented, it is called 49 times during a run and exactly one call matches and sets the flag, so the flag was never the problem. Second, the generic `[Symbol.iterator]` walk in `array_from_spread_value` does **not** miss for a plain array: `js_object_get_symbol_property` synthesizes the BUILT-IN `Symbol.iterator` for an array receiver (a `js_class_method_bind` by name) instead of reading the prototype slot, so the walk resolves the builtin, calls it, and returns the element copy. A guard added to the `js_array_is_array` arm *after* that walk — where the issue points — is dead code; measured, it is never reached.

  So the guard goes **before** the walk, and at each of the four entry points that reach an array by a different route: `array_from_spread_value` (`[...arr]`), `js_array_from_value` (`Array.from`, whose array arm ends in a raw `js_array_clone`), `js_array_push_spread_f64` (spread into an existing array), and `js_array_like_to_array` (call-spread, which decides how many arguments a callee receives). Each delegates to `js_get_iterator`, the one implementation that consults the patched prototype per GetIterator, so the entry points cannot answer differently for the same receiver.

  An **own** `arr[Symbol.iterator]` still wins: the shortcut stands aside when the receiver carries its own method, because `js_get_iterator`'s patched branch reads the prototype only and would otherwise throw "not iterable" for an array with an own method once the prototype slot is deleted.

  Untouched in every ordinary program: `array_proto_iterator_modified()` is sticky-false until user code writes the prototype slot, and #7533's dense fast path already declines when it is set.

  **No gap test, deliberately.** Any test that patches `Array.prototype[Symbol.iterator]` takes the ORACLE down under the parity harness — node builds a `SafeMap` from an iterable and gets the patched value, so `node` exits 1 with `per_context/primordials` and the comparison runs against a crashed reference. Restoring the original first is not available either: reading `Array.prototype[Symbol.iterator]` back yields a prototype-bound method (`next is not a function` when called with `this === arr`), and `getOwnPropertyDescriptor` on a prototype symbol returns `undefined`. Both are pre-existing and filed separately. The fix is verified by direct byte-for-byte comparison against `node --experimental-strip-types` instead.

  Also not fixed here, and filed separately: `for…of` over a *typed local* still ignores the patched method. That is a codegen dense index loop with no runtime call at all — a different mechanism from the four entry points above, needing its own guard.

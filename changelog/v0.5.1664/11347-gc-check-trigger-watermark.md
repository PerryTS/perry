- **perf(gc): `gc_check_trigger` answers "nothing due" from a watermark instead of re-running the due-ladder (#10698).** The allocation-point trigger runs on every `gc_malloc` and every arena block fill, and re-derived its old-reclaim, whole-arena, young-cap and malloc-count arms from a dozen thread-locals each time — ~545 instructions per call under callgrind, almost always to answer "nothing is due". An evaluation that finds nothing due now publishes the two bounds under which that answer keeps holding: the malloc-count threshold, and the young scavenge cap re-expressed as a bound on the inline allocator's current-block offset (the only two ladder quantities that move without a runtime write). The next call compares those two live quantities against the bounds and returns; anything else falls through to the unchanged ladder.
  - **Why a skipped check is one that would have done nothing.** Every other ladder input — the arena/malloc/old-reclaim thresholds, the old-gen and external-side byte counts, `ARENA_TOTAL_BYTES`, the nursery-cap scale and census, the budgeted-cycle flag, the root-lock depth, and the test overrides — is now a `TriggerInput` cell whose `set`/`replace` retire the watermark. It is a type, not a list of call sites: a `Cell` method that does not retire does not exist on it, so a missed writer is a build error. The young generation's sealed bytes are held fixed by retiring on the same two events that invalidate `arena::from_space`'s sealed-bytes cache — a heap-generation advance and `Arena::set_current`. The remaining entry guards (budgeted step, suppression, mid-allocation, unsafe FFI zone) make the full check return without acting too.
  - **Checked, not argued.** Under `cfg(test)` every fast-path answer is re-derived by the full ladder and asserted equal; the whole `perry-runtime` lib suite (4531 tests) passes with that verifier on. New tests in `gc/tests/trigger_watermark.rs` assert the fast path is actually taken on repeated `gc_malloc` (1000/1000 calls), that each bound is the ladder's own threshold (the fast path declines exactly at the malloc trigger and at the young cap, and the ladder then reports that arm due), that each class of input change retires it, and — sabotage — that a watermark the ladder disagrees with trips the verifier.
  - **Measured** (`examples/trigger_bench.rs`, callgrind, shipped `release` profile, loop overhead subtracted): `gc_check_trigger` 544 → 31 instructions per call; `gc_malloc` 775 → 250 (−68%); a runtime arena allocation 97.6 → 96.6, i.e. unchanged. No instruction is added to the compiled inline bump sequence — the young arm reads the offset that sequence already maintains. Keeping the arena path flat took two `#[inline(never)]`s: the watermark retire, and `old_gen_in_use_bytes_add` (a call site in `Arena::try_block_alloc`'s old-gen arm, even untaken, perturbed the inlined Eden bump path's register allocation by +2 instructions per allocation).
  - **Retiring from inside the hot-TLS fill.** `Arena::new` writes `ARENA_TOTAL_BYTES` while the hot-TLS cache is being filled (`ARENA` is one of its named fields), so a retire that resolved the watermark through the cache would re-enter `fill` and the same initializer until the stack overflowed (`trigger_path_tls` caught this during development). The new `tls_hot::hot_if_filled` probes the cache without filling it; before it is filled nothing can have been published, since publishing resolves the cache first, so there is nothing to retire.
  - `scripts/gc_runtime_root_holders.json`: `PASS1_MARKED`'s census window re-audited and re-pinned for the `gc/mod.rs`/`gc/policy.rs` changes (no allocation, relocation, collection or JS callback added; neither window boundary moved); the test-only fast-path hit counter is classified `test_only`.

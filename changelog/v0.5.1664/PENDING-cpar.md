Codegen now schedules module jobs and LLVM unit workers from one budget of CPU slots and memory, sized from the machine. Before, a compile ran at most `min(cpus, 4) / 2` module jobs (2 on any host) and ran every module of 500+ callables or 512+ KiB alone, so a 764-module Next.js standalone server used 2.5 cores of 48 for 18 minutes of codegen. On a 48-CPU slice of a shared 64-core host, that compile now takes 3.5-4 minutes instead of 19-20 (codegen 100-130 s instead of 1,030-1,090 s) and Fastify 35 s instead of 200 s; tsc and Zod, whose time is one module, are unchanged. Every module object is byte-identical to the old schedule's (tsc, Zod, Fastify; Next.js except one module whose object already differs between runs of the old compiler).

The budget's CPU slots are the physical cores among the CPUs the process may run on: unique (package, core_id) pairs from `/sys/devices/system/cpu/cpuN/topology` over the affinity mask, capped by `available_parallelism` (which honours the cgroup CPU quota), and hardware threads where the topology is unreadable. SMT siblings are not counted: on a 48-thread host the default is 24 slots, and compiles are no slower than with 48 (Next.js 4:50 vs 4:42, Fastify 42-51 s vs 45-48 s, tsc and Zod equal) while peak memory is 30% lower. `PERRY_CODEGEN_CPU_SLOTS` sets the number of slots outright. Its memory is three quarters of the smaller of `MemAvailable` and the cgroup v2 headroom (`memory.max - memory.current`), or `PERRY_CODEGEN_MEMORY_MB` when set. Every module job holds one slot plus its estimated peak memory; every LLVM unit worker beyond a module's first holds one slot plus the largest unit's estimate. A job starts only when its memory fits, except when nothing else runs, so a module larger than the whole budget still compiles, alone, and memory in flight never exceeds the budget otherwise.

Modules start largest estimate first, so the long modules begin at once and the small ones fill the remaining slots around them. A waiting unit worker of a running module is admitted before a module job that has not started. The module pool has no more threads than the memory admits jobs of the smallest estimate, so a small budget also keeps the per-thread allocator arenas few: Fastify under `PERRY_CODEGEN_MEMORY_MB=1024` runs 3 jobs and peaks at 1.2 GiB, against 1.3 GiB for the old 2 jobs. Results are collected by module index; the schedule decides when a module compiles, never what it emits.

The estimates come from per-module peaks measured one job at a time (`PERRY_CODEGEN_MEMORY_TRACE=1 PERRY_MODULE_JOBS=1 PERRY_CODEGEN_UNIT_JOBS=1`) over 1,055 modules of tsc, Zod, Fastify and the Next.js server: module = 320 MiB + 500 bytes per source byte + 512 KiB per callable (every measured peak at or below it; closest 326 vs 390 MiB), unit = 64 MiB + 32 bytes per estimated IR byte (largest measured 24).

`PERRY_MODULE_JOBS` still caps concurrent module jobs and `PERRY_CODEGEN_UNIT_JOBS` still fixes unit workers per module. The old "module parallelism: N module jobs x 2 LLVM unit workers" line, whose unit count was not the one codegen used, is replaced by a line naming the budget and what it was derived from. `PERRY_CODEGEN_UNIT_TIMINGS=1` also prints each module job's wall time.

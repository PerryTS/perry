# R9 machine-code finding and bounded follow-up

The original Rust compact admission block is unchanged, but LLVM changes its inlining decisions after the writers gain a second production caller. In main, try_primitive, stringify_record_output::try_object, and stringify_flat::try_object are inlined into js_json_stringify_full. R9's public entry calls all three out of line. The existing heap-string attempt still has no separate call in the full-entry assembly. Public frame grows 272 -> 304 bytes; helper's accepted path has its own 32-byte frame. The new helper uses integer comparisons for true and both zero bit patterns in this build.

The three writers currently use #[inline], not #[inline(always)]. Source search confirms that their only production call sites in R9 are the full entry and the newly added helper (the mod.rs wrapper and other references are cfg(test)). A bounded follow-up is to strengthen only those three annotations, keeping the helper itself #[inline(never)] and leaving all admission, callback, GC, and fallback semantics unchanged. This is unimplemented and unmeasured at the time of this note. Check the resulting assembly; a Rust annotation alone is not evidence that the old entry was restored.

Do not claim frame growth causes any measured regression. Do not normalize zero to undefined: that would widen the known incorrect lazy-source shortcut. Keep baseline lazy-array crashes/output gaps and the separate fractional-spacing difference visible. Any candidate still needs fresh exact production archives, matching worker objects, the same behavior/rooting controls, quiet CPU/RSS comparison, and broader qualification if its focused controls pass.

# Read-only follow-up; no implementation or new profile

The R15 screen's actual-main 1 MiB records-array scan median is 2934.782609 us versus Bun 2226.318841 us (about 31.82% more CPU). R15 itself is 2951.333333 us. These are total workload costs, not a phase attribution.

Source observations on main1a9 (unchanged in R16): parse_api.rs routes eligible 1 KiB..16 MiB top-level arrays through tape construction. json_tape.rs::lazy_get can flip an ascending scan after max(64, length/64) accesses. force_materialize_lazy chooses reparse_materialize while cached_count*2 < length. This can build a syntax tape and later run the DirectParser over the same input. Small cached records already use the existing ConstructionBatch path in json_tape/record_materialize.rs; simply batching that path again is not a new optimization.

A future investigation should first measure phase costs on frozen production bytes, preserving the normal lazy/default path and all sparse/mutation/identity behavior. A construction batch that consumes validated tape entries could potentially remove the second syntax pass, but the current tape walker has extra per-value rooting/allocation and string/number decoding work. Read materialize_value_source, materialize_object, materialize_array, materialize_string_value, materialize_number and reparse_materialize before designing anything. A useful producer must preserve cached output identities and mutations, duplicate/escaped/numeric keys, deep input fallback, callback/spacing semantics, and actual protected moving-GC behavior.

Do not raise the 16 MiB cap or alter the scan threshold to make one row win. Do not treat source comments describing older measurements as new performance evidence. This is a hypothesis and investigation path, not a cause established by profiling and not an implemented R16 change.

Further source observations (still no timing attribution): the general tape object producer allocates an initially empty ordinary object, counts fields, reserves spill, then creates a RuntimeHandleScope per field and uses js_object_set_field_by_name. Lazy string materialization copies a borrowed token to a native Vec before js_string_from_bytes so no moving borrow crosses allocation. Number materialization scans the source token again before f64 parsing. TapeEntry is currently kind/offset/container-link, and leaf link is documented as zero. A bounded, no-callback batch materializer could potentially avoid per-field handle scopes, dynamic property insertion and that defensive temporary copy while suppression covers construction. Reusing leaf metadata for validated token ends is a distinct design possibility; it requires auditing every link consumer and should not silently widen the tape or retain extra source data. None of these proposals is implemented or established as the measured bottleneck.

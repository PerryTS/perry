# Cached construction review

The existing `reparse_materialize` suppression window still encloses the entire producer. The owning lazy header is in a runtime handle; the cached-count predicate refuses null bitmap/cache pointers. Tape, blob and cache slices are created only after suppression begins. No callback runs during the loop. The completed array is pushed to PARSE_ROOTS before suppression ends, then moved into a runtime handle before the existing rooted safepoint and publication patch.

The root array uses the existing `ConstructionArray`: its batched completion installs pointer layout and remembers old-to-young slot pages through `ConstructionBatch::finish_json_slots`. When active marking refuses ConstructionBatch, its ordinary push uses `note_array_slot_layout_only`, which explicitly calls the ordinary slot barrier for born-old arrays. The misleadingly short helper name does not mean those edges are unbarriered. The new 2600-element runtime fixture exercises the large-allocation path with cached aliases and subsequent moving collections; candidate results remain pending until its fresh build is available.

There is no added runtime cache, GC scheduling knob, threshold change or new collector implementation. The existing 294-test JSON suite passed on source 66ae4aaa39c8dee54773393d1c78c64181ae532a, including construction/old-to-young and active incremental-marking tests. Those existing tests are supporting coverage, not a claim that every test directly calls the new producer. The new focused test directly demonstrates skipping a cached subtree by asserting that its source-only property key was never interned.

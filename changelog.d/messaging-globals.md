Two messaging globals fixed. `new BroadcastChannel(name)` without a `worker_threads` import: `postMessage` on one channel now reaches the other channels of its name (the program did not link the stdlib, whose init registers the channel registry and dispatch, so the runtime's fallback object had no transport and delivered nothing); module collection now marks a program that names the `BroadcastChannel` global as needing the stdlib (`collect_modules/feature_detect.rs`). A class declared in a function or block scope under the name of a global built-in constructor (`function f() { class MessageChannel {} }`) is now a scope-local rename like a colliding user class (`LoweringContext::mint_class_rename`): registered under its plain name, it captured every `new MessageChannel()` of the module, so a top-level `new MessageChannel()` built the nested class (`mc.port1` undefined, TypeError). Programs that name neither are unchanged. Fixture `tests/parity/language/scope/test_messaging_globals.ts`.

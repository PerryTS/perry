**fix(gc): a `CannotCollect` helper's registry lock no longer flushes a deferred GC request on release (#11523).**

`perry-codegen`'s `gc_call_effects` classifies the `js_typed_feedback_*` record/observe/guard helpers, `js_gc_note_slot_layout[_aware]` and the `js_closure_set_capture_*` setters `CannotCollect`, so their calls are emitted `"gc-leaf-function"` and RS4GC relocates nothing across them. All of them reach the typed-feedback registry's `GcRootRegistryGuard`, either directly or via `layout_mark_unknown` -> `invalidate_representation_change`. That guard's `Drop` flushed any GC request deferred while the lock was held (`flush_deferred_gc_request`), and the flush can run a moving collection. "Cannot collect" held only because nothing in those regions happened to raise a request, and nothing wrote that down or checked it.

Fix: `lock_gc_root_registry_noncollecting` (`gc/roots.rs`). Its guard records at entry whether a request was already pending, and its release never flushes, at any depth. A request raised inside the region breaks the contract. Under `debug_assertions` (the `gcaudit` profile) and in tests the release panics with `#11523`. Otherwise the request stays pending for the next ordinary release, and its trigger re-arms on the next allocation check. Either way the helper does not collect. The typed-feedback registry is the only user. The contract is documented next to the classification in `gc_call_effects.rs`.

Audit (every root-registry lock reachable from a `CannotCollect` / `AllocNoReentry` entry):
- The typed-feedback `REGISTRY` is the only one. It is reached by `js_typed_feedback_record_guard_{pass,fail}`, `_record_fallback_call`, `_observe_property_{get,set}`, `_class_field_{get,set}_guard`, `_closure_direct_call_guard`, and the plain/numeric array index get/set/push guards. `js_gc_note_slot_layout[_aware]`, `js_gc_key_add_layout_unknown` and `js_closure_set_capture_{bits,ptr}` / `js_closure_set_box_capture_ptr` reach it only when feedback is enabled. Every critical section touches only Rust-heap `HashMap`/`Vec`/`String` state and reads GC headers, so none raises a request. **Kept `CannotCollect`**, now enforced.
- No other `lock_gc_root_registry` user (symbol, promise/native_async, geisterhand, media, messaging, plugin, tui, ui_text, path_registry, arkts) is reachable from the table.
- The `AllocNoReentry` helpers (e.g. `js_array_push_f64`) can reach the same lock through array layout invalidation. That lock no longer flushes, and an ordinary flush would only re-run `gc_check_trigger`, which an allocation in those helpers may already do under the `AllocNoReentry` contract. No reclassification needed.

Tests: `gc/tests/noncollecting_root_lock.rs` plants a real deferred collection request (`gc_collect_minor` under the lock) inside the typed-feedback locked region through a test-only hook. It then drives `record_guard_pass` and the layout path `invalidate_representation_change`, and asserts the release panics, runs no collection, and leaves the request pending. A control test shows the same plant under an ordinary lock does collect on release, which proves the plant is live. A fourth test covers clean regions and requests inherited from an enclosing ordinary lock. Sabotage-checked: with `registry()` reverted to `lock_gc_root_registry`, the two catch tests fail.

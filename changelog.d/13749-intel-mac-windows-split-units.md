**Intel macOS and Windows x64 builds compile again.** Three codegen failures blocked them. (1) On x86_64 Mach-O, a module large enough to split into codegen units failed to assemble with "symbol '…fnname.N' can not be undefined in a subtraction expression": a function's `$info` record names its display name as a 32-bit `name - info` offset, and on Apple targets that name was an alias owned by one unit and declared `external` in the others, which x86_64 Mach-O cannot relocate. The name is now addressed inside the string image, which every unit that needs it defines (as ELF and COFF already did). (2) On Windows, every compile failed on a host whose clang is older than the bundled LLVM (GitHub's windows-2022 image ships clang 20.1.8): the stack-map path printed assembly with LLVM 22 and assembled it with the host clang, which rejected `.seh_startepilogue`/`.seh_endepilogue` and COFF `.section ...,unique,N`. COFF assembly is now assembled in-process by the bundled LLVM (byte-identical to clang 22's output); an external assembler that rejects a directive gets a hint naming `PERRY_LLVM_CLANG`. (3) In split Windows modules the native IR reader refused the TEB load `inttoptr (i64 88 to ptr addrspace(256))` ("cannot materialize `inttoptr`"); it now reads `inttoptr` constants and a load whose pointer is a constant expression. The codegen-unit partitioner also now follows quoted symbol names (`@"\01section$start$…"`), so a later Mach-O unit that names the function-record section bounds declares them instead of failing to parse. (4) On Windows, the first birth of a literal-family object aborted with "literal birth requires a valid literal-section descriptor" (tuichess online mode): the runtime's read-only `.perrylit$a`/`$z` bounds landed in a different output section than the writable descriptors, so the span between them was empty. The bounds are now writable, as `.perrylay`'s already were.

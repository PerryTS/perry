### Fixed

- **`perry-runtime`'s test suite no longer fails at random (#7946).** `cargo test -p perry-runtime` failed **24 runs in 100** on `main` — one or two tests per run, a different test each time — and CI runs `cargo test --release --workspace`, so the red landed on whoever happened to be merging. Every one of the eleven failing tests was the same defect: a **process-global that one test moves and another reads**. libtest runs one thread per test, so a `thread_local!` is per-test and a bare `static` is not, and each of the GC's test locks is taken by the *writer* only. That is the class `per_test_global!` was introduced for in #7672; these are five more instances of it.

  | process-global | moved by | broke |
  |---|---|---|
  | `CLASS_SHAPE_GENERATION` / `ELEMENT_SHAPE_EPOCH` | `invalidate_all_element_shapes()`, i.e. any prototype-method write anywhere in the crate | both `gc::tests::layout_trace::element_shape` cases — `record.generation != class_shape_generation()` retires a proof this thread just established, so `js_array_element_shape_class` reads back `0` |
  | the process **environment**, via `gc::tests::support::EnvVarGuard` (12 sites, 3 knobs) | `PERRY_GC_FORCE_EVACUATE=1` | `gc_force_evacuate_enabled()` is an input to `should_promote_young_in_place()`, so it turned in-place promotion off underneath three `gc::tests::promote_in_place` policy cases |
  | `GC_UNSAFE_ZONES` | `gc::tests::roots`'s `GcUnsafeZoneResetGuard` | `gc_budgeted_start_blocked()` answered "blocked" on every thread, so `complete_budgeted_gc_cycle()` came back `JS_GC_STEP_STATUS_SKIPPED` — both `gc::tests::root_words` cases |
  | `PERRY_GC_POLL_ARMED` / `ARM_EVENTS` | `arm_poll()`, reached from `ScheduleGuard::set` on any thread that pins a GC schedule | both `gc::poll_arm::tests` cases, which assert exact counts |
  | `PERRY_INCREMENTAL_MARK_BARRIER_ACTIVE_COUNT` | any thread running an incremental cycle | the untraced-promotion veto, so `an_untraced_promotion_indexes_the_objects_it_could_not_prove_live` failed with `cycles=0, objects=0` |

  Each is fixed where the codebase already had an answer for it. The element-shape counters become `per_test_global!` (per-thread in a test build, byte-identical `static` in a product build) — `ELEMENT_SHAPES` was already thread-local, so a process-wide generation was only ever reachable by another *test*. `EnvVarGuard` is **deleted**: it took `std::env::set_var` under a mutex, which serialized the twelve tests that set a knob and did nothing for the ~2 200 that read one. Knobs a test needs to move now have a per-thread override next to their reader, the same shape as `barrier_arming`'s `TEST_ARMED_OVERRIDE`; the two `PERRY_CONSERVATIVE_STACK_SCAN` cases are about a precedence *rule*, so the rule became a pure function taking the env answer as an argument (the `parse_promote_in_place` idiom). `gc_blocked_by_unsafe_zone()` gets a per-thread test pin. `poll_arm`'s arm/disarm algebra moves onto a `(&AtomicU32, &AtomicU64)` pair the tests own privately, with a new read-only `the_statics_are_wired_to_the_shared_algebra` so the shipped statics do not go dark.

- **The untraced-promotion veto now asks whether an incremental mark cycle is running *on this thread*, not "anywhere" (#7946).** `PERRY_INCREMENTAL_MARK_BARRIER_ACTIVE_COUNT` is the deliberately conservative cross-thread approximation the write barrier's fast path wants — a false positive there costs one out-of-line call that returns. Here it cost a policy decision, and it was unfounded: arenas, `hot_birth_extra_flags` and the barrier's `valid_ptrs` pointer are all per-thread, so another agent's cycle cannot put a mark on this thread's nursery. Single-threaded the two forms are identical (`incremental_mark_barrier_active()` short-circuits on the same global load); with `perry/thread` agents the old form let one agent's incremental cycle disable another agent's in-place-promotion policy outright. Sabotage-verified by `gc::tests::promote_in_place::another_agents_incremental_cycle_does_not_veto_this_threads_untraced_promotion`, which asserts **both** directions — a foreign arm must not veto, this thread's own barrier must, or #7888's stale-mark hazard is back.

### Changed

- `untraced_promotion_instrument_veto()` returns the **name** of the armed instrument instead of a bool, and a copying minor records why it declined the untraced path, so `cycles=0, objects=0` now says which input moved rather than only that something did. That is what identified the fifth cause above: 21 of 21 recorded failures read `incremental_mark_in_progress`.

### Known remaining

- `gc::tests::runtime_roots::prototype_addr_cache::prototype_addr_reads_through_a_forwarding_stub` still fails about 1 run in 100, tracked as #7955. `ARRAY_PROTO_ADDR` / `OBJECT_PROTO_ADDR` are a process-global cache of a **thread-local** heap address, so the clean fix is the same `per_test_global!` conversion — but that materialises lazily, and the first read on a thread runs a full `globalThis` bootstrap from inside a GC root scan, which deterministically broke two `dead_owner_side_tables` prune cases. Reverted rather than shipped half-understood.

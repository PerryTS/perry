On x86_64 Linux, creating an `Error` no longer costs time proportional to the number of functions in the program. Each captured frame was classified as JS or runtime by a linear scan over every function's metadata (`BundleFunctionNames::contains_key`), so a large program paid that scan for every frame of every `Error`: the Supabase CLI's `--version` spent 43.2 G of its 52.5 G instructions capturing the stacks of 636 Errors that its libraries create while loading.

Codegen now places every body it publishes a named function record for in its own output section, `perry_js_text`, and the capture tells a JS frame by whether its code lies between the linker's `__start_perry_js_text`/`__stop_perry_js_text`: two compares per frame, decided by where the code lives, with no lookup structure. The captured frames are the same as before: only named JS bodies are in the section, and only they count against `Error.stackTraceLimit`.

The link passes `-z start-stop-gc`, so referencing the section's bounds keeps no function alive that `--gc-sections` would otherwise drop. With `--function-order`, ranked JS bodies take their rank inside the JS text section (`perry_js_text.sorted.<rank>`), which the generated linker script gathers at its front; the hot run is now two runs, the runtime's at the front of `.text` and the JS one at the front of `perry_js_text`, and both are huge-page backed. Other targets are unchanged: their frame-pointer walk already skips runtime frames.

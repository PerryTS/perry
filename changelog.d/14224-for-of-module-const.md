Performance: a `for (const x of xs)` walk over a source typed as a Number array (a `number[]` parameter or local, a module `const` or `let` initialized with numbers) answers the IteratorRecord's array-mode proof and the packed-f64 loop admission together, and the counted loop uses that answer instead of calling its own guard. When no program write can reach an iteration member or define an element descriptor, the answer is an inline header test (a non-forwarded plain array in the raw-f64 layout, no integrity flags, default prototype chain, bounded capacity); anything else calls `js_array_record_enter_counted`. Arrays of any other element type skip the admission. In a packed loop, a leading `const x = a[k]` binding of the counter's element is a Number held in a plain F64 slot (no GC root), so a reduce like `s += x` keeps `s` unboxed. The packed read no longer reloads the receiver from its root slot when it uses the hoisted handle, which let LLVM hoist the element-base loads out of the loop. This also applies to hand-written counted loops of that shape and to the IteratorRecord loop's own packed clone. For-of over an 8-element module constant inside an outer loop: 321 to 94 instructions per outer iteration (300 before the source walk; Node 148). The same loop over a `number[]` parameter or a module `let`: 325 to 96–99. The array header constants the inline test reads (`GC_TYPE_ARRAY`, `GC_ARRAY_RAW_F64_LAYOUT`, `GC_ARRAY_CUSTOM_PROTO`, `PACKED_F64_LOOP_MAX_CAPACITY`) now live in `perry-abi`, and the runtime asserts its own copies against them. `PERRY_LITERAL_FOR_OF=0` still selects the IteratorRecord loop alone.

Remove `.` and `..` path segments while parsing a URL, per the WHATWG "path state" (#12864). `new URL("https://x/a/b/../c").pathname` was `/a/b/../c` instead of `/a/c`, so `href` carried the unnormalized text too — the case routers and path-based access checks depend on (`/public/../admin` must read as `/admin`).

Root cause was structural, not a dropped branch: `parse_url` never had the path-state pass at all. It split the authority off the input and stored the remaining text as `pathname` verbatim; every consumer (`create_url_object`, `new URL(str, base)`, `URL.parse`, the `href`/`pathname` setters, `fileURLToPath`) then built on that raw string. WHATWG keeps a URL's path as a *list* of segments and drops dot segments as it reads them, which is why the standard's rules are asymmetric in a way a plain `pop` loop cannot reproduce: a dot segment is dropped, but when it is the LAST thing in the path the parser appends an empty segment instead of nothing, so `/a/..` is `/` while `/a/b/..` is `/a/`.

`crates/perry-runtime/src/url/parse.rs` gains `normalize_hierarchical_path`, the path-shape rules applied to a path string: `.`/`%2e` are single-dot segments, `..`/`.%2e`/`%2e.`/`%2e%2e` are double-dot (ASCII case-insensitive, per the standard), empty segments from a `//` run survive verbatim (`//a/../b` → `//b`), a segment that merely contains a dot is untouched (`/a/.../b`), and the `file:`-only rules apply — a Windows drive letter canonicalizes to `:` (`file:///C|/x` → `/C:/x`) and a path that is only a drive letter is never shortened (`file:///C:/..` stays `/C:/`). `parse_url` applies it to the hierarchical branches only, so an opaque path (`mailto:a/../b`, `data:`) keeps its text.

The same parse pass also had the rest of the special-scheme shape missing, and it is one rule family, so it lands here rather than as a second defect:

- **`\` is a separator for special schemes.** `http://x\a\b` is `http://x/a/b` and `\` terminates the authority, so folding happens before the host is read. Query and fragment keep theirs — their encode sets do not encode `\` (`?q=\a`, `#f\b`) — and a non-special path keeps them too (`foo://a/b\c` is `/b\c`). A backslash in a non-special *host* is a forbidden host code point, so `foo://a\b` is now invalid, as in Node.
- **The `//` after a special scheme is optional and its separator run is skipped.** `https:x`, `https:/x` and `https:\x` host `x`; `https:///x` and `https:////x` do too. Special schemes are therefore never classified as opaque, while `file:` keeps its own separator rules: extra separators are path (`file:////x` is an empty host with the path `//x`), its host may be empty (`file:`, `file:x`, `file:/x`), and `file:\\host` carries an authority marker written with backslashes.
- **`file:` hosts canonicalize like any other special scheme's** (`file://SERVER/x` → `server`, `file://123/x` → `0.0.0.123`, `file://LOCALHOST/x` → empty host). They previously skipped the WHATWG host parser entirely.
- **`is_valid_absolute_url` mirrors all of the above** instead of requiring a literal `//` for a special scheme, and no longer rejects an opaque URL with nothing after the colon (`mailto:` is valid, as in Node).

`js_url_set_pathname` runs the same states, because assignment clears the path and re-parses the value: a special scheme folds `\`, the value gains a leading separator when it has none (`\a\b` and `b\..\c` both root), dot segments and a `file:` drive letter are canonicalized, and a non-hierarchical URL is left alone.

Note the fast-path guard in the dot-segment pass: it must skip work only when the path has neither `.` nor `%`. `%2e` contains no literal dot, so a `.`-only check silently returned the unnormalized path for every percent-encoded dot segment — caught by the new unit test rather than by reasoning.

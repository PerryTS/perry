Locale and dynamic string paths no longer hold a raw string address while user code runs (#12539). `localeCompare(that, locales, options)` now reads `locales` and `options` exactly once, in Collator order, before either string address is taken, and hands the comparison the resolved `numeric` flag (`js_string_resolve_collator_args` + `js_string_locale_compare_resolved` replace `js_string_validate_collator_args` + `js_string_locale_compare_opts`). The `numeric` getter used to run twice, the second time while the receiver and `that` were held raw, and the options object itself was held raw across `CanonicalizeLocaleList`. `toLocaleUpperCase` / `toLocaleLowerCase` resolve `locales` through `CanonicalizeLocaleList`, so array-likes, getters and `toString` entries now behave as they do in Node (Turkish/Lithuanian casing, TypeError on a non-string entry); the receiver stays rooted across that resolution. In the runtime's dynamic string-method table, `substr` roots its receiver and its raw `length` while `start` coerces, and `charAt` / `at` / `charCodeAt` / `codePointAt` coerce the position before reading the receiver. New gap test: `test_gap_gc_locale_options_rooting.ts`.

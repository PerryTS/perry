**Merge `main` (v0.5.1581 → v0.5.1593) into the turnloop branch, and port #10447 onto P3's timer store.**

The branch was 94 commits behind and CONFLICTING, which means it had been
receiving essentially no CI: GitHub does not schedule `pull_request` workflows
on a conflicting PR, so the rollup reads "pending" rather than red.

Only **two** of those 94 commits touched the timer module, which is what made
the conflict tractable — the large conflict regions were P3's restructure
against code it had deleted, not main making large timer changes.

- **#10420** (more than 8 trailing `setTimeout` args clamped to 9, silently
  dropping the rest) was **already fixed here**: P3's dispatch uses
  `js_closure_call_array`.
- **#10447** was **not**, and this is the substantive part of the merge.

Main's #10447 fixed a bounded id→ref-state registry that evicted the oldest ids
by insertion order whether or not they were still scheduled, so 65,536 later
timers silently undid a live timer's `unref()` and dropped the id out of
`is_known_timer_id`. Our copy still carried the comment claiming "an evicted id
is never re-queried in practice" — the exact claim #10447 disproved.

Half of it never bit this branch: P3's keep-alive reads
`store::has_refed_timers()`, not the registry, so the "process stays alive
forever" symptom did not apply. The half that did is
`.hasRef()`/`.ref()`/`.unref()`/`.constructor` quietly ceasing to dispatch once
an id was evicted.

The fix auto-merged into `ref_states.rs` (this branch never touched that file)
but it REPLACED the API, and a plausible text merge compiles while leaving the
fix inert — which is exactly what happened on the first attempt here, caught by
`-D warnings` reporting `schedule` and `retire` as never used. Ported properly:

- `register_scheduled_timer(id, kind)` returns a `ScheduledTimerId` guard, now
  held by `store::Entry`. Dropping the entry retires the id, so no removal site
  can forget to, and a queued timer can never be evicted out from under its
  handle methods.
- `duplicate_for_rearm` takes `&mut self` to MOVE the guard into the re-armed
  copy. libuv re-arms an interval before running its callback, so two entries
  briefly exist for one id; the copy is the live timer. Leaving the guard on the
  dispatched entry would retire the id the moment the callback finished.
  `ScheduledTimerId` is deliberately `!Clone`, so the borrow checker refuses the
  mistake rather than allowing a silent double-retire.
- `TIMER_HANDLE_KINDS` is deleted. It was a second table with the same evicting
  cap *and* an O(n) `min()` scan per insert; the kind now lives in the registry
  entry, so `.constructor` on a live timer keeps working for the same reason
  `.hasRef()` does.
- The registry is added back to `timer_tables_census()`: it is a bounded side
  table that outlives its queue entries, and leaving it out under-reports what
  timers retain.
- Main's `RefStatesView`/`with_ref_states` are deliberately NOT carried over.
  They existed so `ownership.rs` could scan the global `CALLBACK_TIMERS`/
  `INTERVAL_TIMERS` vectors under one registry lock; P3 replaced those globals
  with a per-agent store that carries `refed` on the entry, so there is no batch
  scan left to amortise. Removed rather than left dead, per CLAUDE.md's
  kill-policy.

Main's own regression test for #10447 now runs here, with one assertion adapted
and the reason recorded in the test: P3 repurposed the three liveness entry
points, so `js_callback_timer_has_pending` answers the *check* phase
(`setImmediate`) while `js_timer_has_pending` answers the timeout classes. The
generated loop's disjunction asks all three, so the union is unchanged — but an
assertion about a `setTimeout` belongs to the first accessor here, not the third.
**Sabotage-checked:** dropping the guard instead of storing it fails that test
with "timer 1 dropped from the registry", the #10447 symptom exactly.

Two modify/delete conflicts were resolved by checking rather than by picking a
side. `perry-ext-fetch` stays deleted: main's #10360 fix lives on in
`perry-stdlib/src/fetch/response_ctor.rs`, which cites the issue by number and
carries both halves — the null-body-status TypeError and the `--platform bun`
skip — with `Response.json` sharing the same `response_init`.
`timer/ownership.rs` stays deleted, its two surviving functions having moved to
`timer.rs` and its three `has_refed_*` replaced by the store's counters.

`gc_runtime_root_holders.json` was unioned structurally by `(file, name)` rather
than merged as text. One entry, `PASS1_MARKED`, had been re-audited by BOTH
sides for different reasons — this branch for turnloop P0's
`shutdown_wait_driver()` call, main for the copying minor's
`copying_parent_facts` module. The merged tree contains both changes, so the
entry carries both audit tails and the window's `gc/mod.rs` pin is updated to
the merged file; taking either side alone would have left a real change
unaudited, which is the one thing that gate exists to prevent.

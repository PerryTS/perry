### Fixed

- **`import { z } from "zod"` → `z.map(...)` threw `TypeError: object is not a function` (#7154).** HIR lowering rewrote `<importedIdent>.<name>(...)` into the matching `Expr::Array*` builtin on the strength of the **method name alone**. Any named import whose member happens to be called `map`, `filter`, `find`, `forEach`, `reduce`, `reduceRight`, `slice`, `includes`, `indexOf`, `keys`, `values`, `entries`, `flat`, `with`, `toSorted`, `toReversed` or `toSpliced` was routed to `Array.prototype`: every argument past the first was dropped and argument #1 landed in the builtin's callback / index / separator slot.

  zod is the headline victim because `zod/src/index.ts` is `import * as z from "./v4/classic/external.js"; export { z };` — `import { z } from "zod"` is a *named* import of a module-namespace object, which the #321 `namespace_import_locals` guard does not cover. `z.map(keyType, valueType)` lowered to `Expr::ArrayMap { array: z, callback: keyType }` (`--trace hir`), so `js_validate_array_callback` threw before zod's `map` ever ran.

  Only `join` (#420, drizzle's `sql.join(list)`) and `sort` (semver's `sort(list)`) had ever been given the "is this actually an array?" guard. **New invariant, applied once for every method name:** fold only when the imported binding is statically typed as an array (`Type::Array` / `Type::Tuple` / `Type::Generic<Array|ReadonlyArray>`); `Type::Any` — the fallback used when nothing is known — is not evidence. Everything else falls through to the generic call path, which invokes the member itself with all of its arguments.

  Regression coverage: `test-files/test_gap_imported_member_array_method_names.ts` exercises 19 misnamed members on an imported plain object plus 19 real-imported-array methods (both directions), and is byte-exact against Node 26.5.1; it throws `TypeError: number 1 is not a function` on the unfixed compiler. Unit tests in `crates/perry-hir/src/lower/expr_call/imported_array_methods.rs` pin the predicate both ways.

  Known cost, deliberately taken: `lookup_extern_func_types` only records types for body-less `declare function` FFI declarations, so a real `export const arr = [1, 2, 3]` also arrives as `Type::Any` and now takes generic dispatch instead of the array intrinsic. That path is byte-correct (all 19 array cases in the new gap test); restoring the intrinsic needs cross-module const-value types.

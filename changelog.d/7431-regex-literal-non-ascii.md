**Raw non-ASCII characters in a regex literal are no longer decoded as Latin-1 (#7426).** `/€/` never matched, `/a€b/.source` reported `"aâ\x82¬b"` with `.length` 5 instead of 3, and every literal-taking string API went with it — `replace`, `split`, `match`. Nothing errored; the pattern silently stopped matching, which made Perry unusable for non-English text processing (the report came from parsing German invoices, where every amount ends in ` €`). The fault was not in the regex engine or in HIR lowering but in the parser's identifier-escape pre-pass, `normalize_unicode_identifier_escapes`, which rewrites the source *before* SWC sees it: every state in that scanner steps by whole characters via `source[i..].chars().next()` / `len_utf8()` except `State::Regex`, which stepped one **byte** at a time and widened each with `bytes[i] as char` — a Latin-1 decode, so the three UTF-8 bytes of `€` (`E2 82 AC`) reached SWC as the three codepoints `â` `\u{82}` `¬`. That asymmetry is exactly why string literals, template literals and non-ASCII identifiers were unaffected, why `\u`/`\x` escapes worked (ASCII, so byte-stepping is lossless), and why `new RegExp("€")` was correct while `/€/` was not — the constructor's argument is a *string* literal, which took the correct path. The regex state now steps by chars in both the backslash arm (an identity-escaped non-ASCII char, `/\€/`, took the same corrupting path) and the default arm; every structural byte the state machine tests (`\` `[` `]` `/`) is ASCII and UTF-8 continuation bytes are `0x80..=0xBF`, so character-class and terminator tracking are unchanged and all-ASCII patterns are byte-for-byte what they were. Verified both directions: the new gap twin `test_gap_7426_regex_literal_non_ascii.ts` is byte-identical to Node 26.5.1 after the fix and diverges on 20 of its 27 lines against a pristine rebuild from `HEAD`, so it cannot pass vacuously. Three new `perry-parser` unit tests land in the per-PR `cargo-test` job, including the guardrail in the other direction (identifier escapes outside a literal still normalize, `\u` escapes inside one stay escapes, `/` inside a character class still does not terminate the pattern).

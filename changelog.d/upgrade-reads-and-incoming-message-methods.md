- **http/net/ws: an `'upgrade'` listener now receives what the client sends (#10470, #10471).** The listener got a writable `net.Socket` and a Buffer `head`, and its own `101` reached the client, but `socket.on('data')` never fired, and neither did `'end'`/`'close'`. Two independent defects, both required for the fix:
  - **The bytes were dropped before reaching `net`.** The handoff (`turnloop_net::transfer` + `perry_ext_net::adopt_turnloop_upgrade`) points the connection's completions at perry-ext-net's subsystem slot, and the runtime silently drops a completion for a slot with no sink. perry-ext-net installs its sink lazily in `turnloop_io::enabled()`, which neither the adoption nor a socket write reaches. In a program that only runs an HTTP server, every inbound byte and the EOF were therefore lost. `adopt_turnloop_upgrade` now installs the sink itself. It runs on the loop thread inside the completion that decoded the upgrade, so no read can land between the transfer and the registration. The client-side `'upgrade'` handoff (`client_turnloop::handoff`) goes through the same function and gets the same fix.
  - **The `'data'` listener was filed in the wrong registry.** HIR's upgrade pre-scan types the listener's second parameter as a native `("ws","Client")`, even when it is declared `any`. That is the Perry-native `wsId` surface a server with an attached `WebSocketServer` still uses. So `socket.on('data', cb)` compiled to `js_ws_on_client_i64`, which filed the listener in the ws table under the socket's id, where nothing ever fires it. `socket.write` has no ws row and already dispatched dynamically, which is why writing worked. `js_ws_on_client_i64` now forwards `on`/`addListener` to the runtime's dynamic method call when the id is not a ws connection (`WsClientHandle`), so the listener reaches perry-ext-net. A real ws id keeps its own listeners. No signature changed.

  This unblocks `ws`'s `WebSocketServer` and any hand-rolled upgrade protocol. Tests: `perry-ext-net` `tests/turnloop_upgrade_reads.rs` is a one-test integration binary, because the sink registry is process-global and in the lib test binary another test always installs the sink first. `perry-ext-ws` `tests::client_on_forwards_a_foreign_handle_and_keeps_its_own` covers the forwarding. Each fails without its fix.
- **http client: `IncomingMessage` methods read as functions through dynamic dispatch (#10670).** On an `any`-typed client response (how an npm package looks after type stripping), `typeof res.pipe`, `res.on`, `res.once`, `res.addListener`, `res.pause` and `res.resume` read `undefined`, so `const pipe = res.pipe; pipe.call(res, dest)` threw. The one method the property path did expose, `setEncoding`, was bound to `handle as f64`, a numeric conversion rather than the NaN-boxed handle, so calling it threw `(number).setEncoding is not a function`. Both perry-ext-http's `client_dispatch_ext` and perry-stdlib's mirror arm in `dispatch_http.rs` now bind every method the method arm answers to the POINTER_TAG-boxed handle. The stdlib method arm also gains `pause`/`resume` so the two vocabularies match. A direct `res.pipe(dest)` call already worked on `main`. Test: `perry-ext-http` `client_dispatch_ext::tests::incoming_message_methods_read_as_functions_bound_to_the_response`, which fails without the fix.
